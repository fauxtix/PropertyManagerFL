# AGENTS.md

## Repo shape
- `PropertyManagerFL.sln` is the build boundary: 6 projects (Core, Application, Infrastructure, Api, UI, EmailService). Five other `.csproj` files sit outside it (`Client.Infrastrucure` [sic], `Shared`, `Sql`, `Logging`, `Application/Shared/CommonLayer`); `Logging` is empty but still referenced by Api.
- User-facing setup docs: `README.md` / `README-EN.md` plus `docs/DATABASE.md`, `docs/LOCAL-SETUP.md`, `docs/SYNCFUSION-LICENSES.md` (key version/editions) and `docs/PRODUCTION.md`. Keep them in sync when ports, scripts, secrets or Syncfusion versions change.
- Two web apps must run together: `PropertyManagerFL.slnLaunch.user` starts API, then UI (both `Action: Start`). UI is Blazor Server; it calls the API via `ApiWrappers/*` HttpClient wrappers **and** references Infrastructure directly (repositories registered in `UI/Configuration/DependencyInjectionConfig.cs`). Because the solution launch already starts both, never leave manually started `dotnet run` instances behind after a smoke test — stop them and free ports 5000/5001/5152/7181 so the user's own launch is not blocked.
- API/UI DI, AutoMapper and FluentValidation setup lives in parallel `Configuration/*.cs` files and is near-duplicated; changes often need both. Entry points are `Api/Program.cs` and `UI/Program.cs`.

## Commands / verification
- Build: `dotnet build PropertyManagerFL.sln`
- Run locally in two terminals: set `$env:ASPNETCORE_ENVIRONMENT = 'Development'` first, then `dotnet run --project PropertyManagerFL.Api` and `dotnet run --project PropertyManagerFL.UI`. The shell may already have `ASPNETCORE_ENVIRONMENT=Production`; in Production user-secrets are not loaded (API returns 401) — supply values via environment variables instead.
- URLs: **Development, Kestrel** (profiles `PM.WebApi` / `PropertyManagerFL.UI`) — API `https://localhost:5001;http://localhost:5000`, UI `https://localhost:7181;http://localhost:5152` (the original values from git, restored on 2026-11-23). The `iisSettings` entries (`5010`/`44301`, `31859`/`44350`) belong to the separate **IIS Express** launch profile and are only used when that profile is selected in Visual Studio; `dotnet run` and the solution launch use Kestrel. **Production/IIS** uses API `http://localhost:4300`, UI `https://localhost:4310`. Since IIS occupies 4300/4310, Development must not use them.
- Build + tests: `dotnet build PropertyManagerFL.sln` and `dotnet test PropertyManagerFL.Tests/PropertyManagerFL.Tests.csproj`. CI is `.github/workflows/ci.yml` (build + test on Ubuntu); CD to IIS is `.github/workflows/cd.yml` (self-hosted runner, `workflow_dispatch`). Verification = build + tests + manual smoke test (login, properties/tenants CRUD, payment, letter/PDF, upload).
- When the user reports a UI problem during a local task, assume they are testing the **Development Kestrel** instance (API 5001 / UI 7181). Run it, measure it in the browser and fix the source. Do not explain the symptom away as IIS/Production, a stale deploy or browser cache; IIS 4300/4310 is only in scope after an explicit deploy request.

## Deployment
- `ci.yml` does not deploy. `cd.yml` publishes API to `C:\inetpub\wwwroot\PropertyManagerFL\Api` (HTTP 4300) and UI to `C:\inetpub\wwwroot\PropertyManagerFL\UI` (HTTPS 4310), creating the sites/pools if missing.
- The runner must be registered **in this repository** with the label `iis-propertymanager`; runners are repo-scoped, so a runner registered for another app cannot run these jobs.
- Required GitHub secrets: `PM_API_KEY` (same value in API and UI), `PM_SYNCFUSION_LICENSE` (UI), `PM_SYNCFUSION_LICENSE_API` (API — **both secrets should hold the same valid 35.2.x key**; the API previously had a stale 24.x key and was aligned with the UI on 2026-11-24), `PM_PMCONNECTION`; also `PM_JWT_SECRET`, `PM_JWT_ISSUER`, `PM_JWT_AUDIENCE`, `PM_JWT_EXPIRA_EM_MINUTOS` (API startup validates the JWT secret) and `PM_EMAIL_USERNAME`, `PM_EMAIL_SMTPSERVER`, `PM_EMAIL_PORT`, `PM_EMAIL_PASSWORD`, `PM_EMAIL_FROM` (UI startup requires the email section). Optional `PM_UI_CERT_THUMBPRINT` selects an existing certificate for the 4310 HTTPS binding (otherwise the workflow creates a self-signed localhost certificate). The deploy script injects these into the published `web.config` as environment variables because Production does not load user-secrets — **except `PM_PMCONNECTION`**, which is used only by the script itself for backup-folder ACLs; `ConnectionStrings__PMConnection` is not injected, and `appsettings.Production.json` in API and UI already points at `PropertyManagerDB_Production`.
- `Properties/PublishProfiles/FolderProfile.pubxml` are stale (`net7.0`) and are not used by CI/CD.
- `dotnet publish --no-build` fails with MSB3030: the empty `PropertyManagerFL.Logging` project emits no DLL. Publish with a build (as `cd.yml` does).
- The CD grants Modify on every runtime write folder: `Api\Reports\Docs` (templates + generated letters), `UI\wwwroot\uploads` (property/tenant/unit uploads), `UI\Data\Files` (FileManager), `Api\uploads` and `Api\wwwroot\uploads` (image uploads), `C:\inetpub\wwwroot\PropertyManagerFL\Backups`, plus the `BackupBaseDados`/`BackupOutrosFicheiros` paths read from `ApplicationSettings` at deploy time. The SQL service account is also granted on database backup folders. The Blazor Server UI runs on the server and writes absolute paths returned by the API; `Access to the path ... is denied` means the ACL was not applied (or the CD was not rerun), not that the path is from the client PC.
- SDK pinned by `global.json` to 10.0.404 (`rollForward: latestPatch`); `dotnet --version` in this repo returns 10.0.x even though SDK 11 is installed machine-wide. No `Directory.Build.props`, lockfiles or NuGet config. Projects in the solution now target `net10.0`; the 5 orphan `.csproj` outside it still target `net6.0`.

## Config / environment gotchas
- Both web projects set `UserSecretsId`; supply real values via user-secrets/env. Checked-in `PMConnection` strings point at `DESKTOP-SLIMNUD\SQLEXPRESS` and must be overridden locally.
- `BaseUrl` exists only in UI `appsettings.Development/Production`, not the base file. Development must be `https://localhost:5001/api` (Kestrel); Production uses `http://localhost:4300/api` (IIS). The UI `ApiWrappers/*`, `WrapperNotifications.HubUrl` and `Components/FileUploadComponent.razor` all derive their URLs from it. Pointing Development at 4300 makes the UI talk to the IIS API instead of the Dev API.
- `ApiKey` is the real API gate: global `ApiKeyMiddleware` checks one header on every request, added by UI via `Services/ClientApi/HttpClientConfigurationService.cs`. JWT is mostly unused/misconfigured (`Issuer` vs `ValidIssuer`); do not assume `[Authorize]` protects endpoints.
- `SyncfusionLicenseKey` is a placeholder in appsettings but registered in both `Program.cs` files; a valid key is required for the Syncfusion UI.
- DB setup is manual: `Infrastructure/Database/*.sql` (WorkingTables, LookupTablesWithData, StoredProcedures, Views, UsersAndSchemas) or `SqlData_Script/PropertyManagerDB.sql`. The latter is a **generated snapshot of the cleaned `PropertyManagerDB_Production`** (2026-11-25): full schema plus reference/config data only, no operational/sample rows; `ApiKey`/backup paths are placeholders and SMTP identity fields are NULL. Do not hand-edit it; regenerate from a cleaned DB with SMO. `SqlData_Script` contains only this file (the old `RentsDB.db.sql` and `Sps_Arrendamentos.sql` were removed). EF migrations are commented out in `Api/Configuration/DataBaseConfig.cs`; local `dotnet-ef` tool manifests exist but are unused.
- Notifications: `dbo.Notifications.SuggestedAction` plus 8 `usp_Notifications_*` procedures. Older Dev/test DBs need only the idempotent `ALTER` + re-run of `usp_Notifications_Insert`/`GetForUser` (documented in `docs/DATABASE.md`); fresh installs use the generated script. User-facing alert rules (overdue rent, missing letter, rent due soon, unanswered revocation letter, missing lease document) are described in the READMEs and the four `Help*.md` files. Never use repo SQL scripts on the Production DB.
- Serilog `appsettings` sections are ignored; logging is configured in code to the MSSQL `PMLogs` sink. API also calls `XmlConfigurator.Configure("log4net.config")` although no such file exists.
- The 8 tracked `Api/Reports/Docs/*.dotx` letter templates are runtime assets read from `ContentRootPath/reports/docs`. `Api.csproj` copies them to publish output; CI (`ci.yml`), CD (`cd.yml`) and `deploy-iis.ps1` assert they are present. Never fix a missing IIS folder by copying files by hand — fix the publish rule and redeploy.
- Treat checked-in config values and generated documents under `Api/Reports/Docs/` as sensitive/placeholder; never commit real tenant data.

## Code traps
- Compile-time exclusions mean edits have no effect unless the csproj changes: `Api/Controllers/LoginAccessController.cs`, `Api/Filter/AuthorizationFilterAttribute.cs`, `Infrastructure/Services/AppManagerServices/**`, `UI/Pages/Admin/ViewLogins.razor`, `UI/wwwroot/EstateAgency/**`.
- Don't hand-edit committed generated files: `Core/Datasets/TableAdapters.Designer.cs`, `UI/Resources/*Designer.cs`, `UI/Data/Scheduler/ScheduleData.cs`.
- Add new AutoMapper profiles to both `Api/Configuration/AutoMapperConfig.cs` and `UI/Configuration/AutoMapperConfig.cs`; the UI registers only a subset.
- `LookupTablesController` passes raw table/column names into `LookupTableRepository`; changing that shape affects UI wrappers too.
- ~188 `NotImplementedException` throws exist across wrappers/repositories; check whether a missing behavior is a stub before debugging callers.

## Implementation handoff (`backup.md`)
- For any multi-step implementation, create `backup.md` in the repo root before starting. It is transient local state (gitignored), not documentation.
- Update it after every meaningful step, before risky edits, and at the end of every session. Append timestamped entries; keep a short `Resume here` block at the top. Never put secrets, credentials or tenant PII in it.
- Record: goal/scope, current phase and exact next action, completed steps with commands and results, files changed, verbatim errors, verification done, open decisions/blockers, and any "do not do X" warning discovered.
- On resume: read `backup.md` first, then run `git status --short` and verify the recorded last-good build/smoke state before continuing. Do not rely on conversation memory.
- Delete `backup.md` only after the implementation is verified and the user confirms success; create a fresh one at the start of the next multi-step task.
